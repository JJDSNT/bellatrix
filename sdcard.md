```markdown
# Bellatrix SD Card Performance Investigation Plan

## Comparing SD Drivers and Filesystems on AROS m68k-emu68

**Status:** Investigation Plan  
**Target:** Bellatrix / Raspberry Pi 3B  
**Filesystems:** FAT and SFS  
**SD Drivers:** Bellatrix/AROS driver and Emu68 driver  
**Benchmark policy:** Multiple independent tests; xSysInfo is one optional diagnostic tool, not the primary benchmark

---

# 1. Purpose

Bellatrix currently appears to have lower-than-expected SD card performance.

The purpose of this investigation is to determine **where the performance loss occurs** before attempting optimization.

The primary variables to investigate are:

1. the Bellatrix/AROS SD driver;
2. the Emu68 SD driver;
3. FAT;
4. SFS;
5. interactions between a filesystem and a particular driver;
6. request size and request pattern;
7. alignment and transfer constraints;
8. buffering or DMA behavior;
9. synchronization and scheduling overhead;
10. possible overhead at the Emu68/Bellatrix/hardware boundary.

The investigation must be measurement-driven.

The objective is not initially:

> Make SD faster.

The objective is:

> Determine at which layer Bellatrix loses SD performance, under which workload, and relative to which reference configuration.

---

# 2. Experimental Matrix

The core experiment is a 2×2 matrix:

| Configuration | SD Driver | Filesystem |
|---|---|---|
| A | Bellatrix/AROS | FAT |
| B | Bellatrix/AROS | SFS |
| C | Emu68 | FAT |
| D | Emu68 | SFS |

This matrix is the central reference for the investigation.

As far as practical, all other variables must remain unchanged:

- same Raspberry Pi 3B;
- same physical SD card;
- same Bellatrix build;
- same AROS build;
- same Emu68 build;
- same CPU/JIT configuration;
- same partition sizes where practical;
- same test files;
- same benchmark procedure.

Changing multiple variables simultaneously makes the results difficult to interpret and should be avoided.

---

# 3. What We Need to Separate

There are several different performance layers:

~~~text
Application / benchmark
          │
          ▼
       AROS DOS
          │
          ▼
     FAT or SFS
          │
          ▼
     device layer
          │
          ▼
      SD driver
          │
          ▼
   SD controller
          │
          ▼
       SD card
~~~

A slow file operation does not necessarily mean that the SD driver itself is slow.

Likewise, good raw/device throughput does not prove that the driver behaves efficiently under the I/O patterns generated by a filesystem.

The investigation must therefore test more than one layer.

---

# 4. Benchmark Strategy

Do not designate a single program as the authoritative benchmark.

Use several complementary measurements.

At minimum, try to obtain measurements for:

1. sequential file reads;
2. sequential file writes;
3. small-file operations;
4. random/seek operations;
5. device-level or raw transfer performance where possible;
6. real-world operations such as boot or application loading.

xSysInfo may be used as one additional measurement source.

The value of a benchmark comes from understanding **what path it actually exercises**.

---

# 5. Filesystem-Level Sequential Read Test

A simple sequential file read should be one of the primary tests.

Conceptually:

~~~text
Open()
   │
   ▼
Read()
   │
   ▼
Read()
   │
   ▼
...
   │
   ▼
Close()
~~~

Use a sufficiently large file so that startup overhead does not dominate the result.

A useful initial size is approximately:

~~~text
32 MiB – 128 MiB
~~~

depending on available memory and storage.

Record:

- total bytes;
- elapsed time;
- throughput;
- buffer size used by the benchmark.

For example:

~~~text
Filesystem: SFS
Driver: Bellatrix
File size: 64 MiB
Read buffer: 64 KiB

Time: ...
Throughput: ... MiB/s
~~~

Run the identical test for all four configurations.

---

# 6. Sequential Write Test

Perform the equivalent test for writes.

Conceptually:

~~~text
Open()
   │
   ▼
Write()
   │
   ▼
Write()
   │
   ▼
...
   │
   ▼
Close()
~~~

Record:

- total bytes;
- elapsed time;
- throughput;
- write buffer size.

Be careful about caching.

A filesystem may report completion before all physical activity has finished.

Where possible, make sure the test represents completed filesystem/device work rather than only memory-to-cache throughput.

---

# 7. Buffer Size Sweep

Do not test only one application-level I/O size.

Run sequential tests with several buffer sizes.

For example:

~~~text
512 B
1 KiB
4 KiB
16 KiB
64 KiB
256 KiB
~~~

This can reveal an important class of performance problems.

For example:

~~~text
                  Bellatrix       Emu68

512 B                0.5            0.6 MB/s
4 KiB                3.0            4.0 MB/s
64 KiB               4.0           18.0 MB/s
256 KiB              4.1           18.5 MB/s
~~~

Such a result would strongly suggest that the Bellatrix path is failing to benefit from larger requests.

Conversely:

~~~text
                  Bellatrix       Emu68

512 B                0.5            0.6 MB/s
4 KiB                3.5            3.7 MB/s
64 KiB              17.5           18.0 MB/s
256 KiB             18.0           18.4 MB/s
~~~

would indicate reasonably normal scaling with request size.

---

# 8. Small-File Workload

Sequential throughput alone is insufficient.

Create a workload involving many small files.

For example:

~~~text
create N files
write small amount to each
close each file
reopen files
read files
close files
~~~

Measure separately if practical:

- creation time;
- write time;
- open time;
- read time;
- deletion time.

This is particularly useful when comparing FAT and SFS because metadata behavior may differ substantially.

---

# 9. Random / Seek Workload

Test repeated:

~~~text
Seek()
Read()
~~~

operations across a larger file.

This workload is useful for detecting:

- latency;
- excessive command setup overhead;
- filesystem metadata overhead;
- small-request penalties;
- synchronization costs.

Sequential throughput can hide all of these.

---

# 10. Device-Level Testing

Where possible, include a test that bypasses ordinary file operations and exercises the device path more directly.

Conceptually:

~~~text
benchmark
    │
    ▼
device I/O
    │
    ▼
SD driver
    │
    ▼
SD controller
    │
    ▼
SD card
~~~

This is important because it allows comparison with:

~~~text
file benchmark
    │
    ▼
DOS
    │
    ▼
FAT / SFS
    │
    ▼
device
    │
    ▼
SD driver
~~~

If device-level performance is already poor, filesystem investigation becomes secondary.

If device-level performance is good but filesystem-level performance is poor, the investigation moves upward toward request patterns and filesystem/device interaction.

---

# 11. xSysInfo

xSysInfo is available as an additional diagnostic option:

~~~text
https://github.com/reinauer/xSysInfo
~~~

It should **not** be treated as the primary or authoritative benchmark.

Its results should instead be added to the evidence collected from the other tests.

The exact path exercised by the relevant xSysInfo drive benchmark should be verified from its source before interpreting the numbers.

Recent versions contain handling relevant to Amiga-style storage devices, including concepts such as:

- `DosEnvec`;
- `MaxTransfer`;
- `Mask`;
- device transfer constraints.

This makes xSysInfo potentially useful for exposing differences between the Bellatrix and Emu68 storage configurations.

However:

> Do not infer FAT vs SFS performance solely from an xSysInfo drive-speed result unless the tested xSysInfo code path demonstrably exercises the filesystem itself.

Use it as one additional data point.

---

# 12. Real-World Tests

After synthetic measurements, collect at least one real-world measurement.

Candidates include:

- AROS boot time;
- time until Wanderer is usable;
- loading a large application;
- directory scanning;
- copying a representative directory tree.

These measurements are useful because a driver can perform well in a sequential benchmark but poorly under actual OS workloads.

However, real-world measurements should be interpreted only after lower-level measurements exist.

For example:

~~~text
Boot is slow
~~~

is an observation.

It is not evidence by itself that:

~~~text
SD driver is slow
~~~

because boot involves many additional subsystems.

---

# 13. Cache Effects

Distinguish where possible between:

~~~text
cold read

SD card
   │
   ▼
filesystem
   │
   ▼
memory
~~~

and:

~~~text
warm read

filesystem cache
      │
      ▼
    memory
~~~

If running the same test twice produces substantially different results, record both.

Do not silently average cold and warm results together.

The difference itself may provide useful information about caching behavior.

---

# 14. Initial Testing Sequence

The recommended initial sequence is:

~~~text
1. Verify FAT with Bellatrix driver
                 │
                 ▼
2. Verify SFS with Bellatrix driver
                 │
                 ▼
3. Verify FAT with Emu68 driver
                 │
                 ▼
4. Verify SFS with Emu68 driver
                 │
                 ▼
5. Sequential read/write tests
                 │
                 ▼
6. Buffer-size sweep
                 │
                 ▼
7. Small-file test
                 │
                 ▼
8. Random/Seek test
                 │
                 ▼
9. Device-level benchmark where available
                 │
                 ▼
10. Optional xSysInfo measurements
                 │
                 ▼
11. Compare results
~~~

Only after this baseline exists should invasive driver instrumentation begin.

---

# 15. Result Table

Maintain a table similar to:

| Test | Bellatrix + FAT | Bellatrix + SFS | Emu68 + FAT | Emu68 + SFS |
|---|---:|---:|---:|---:|
| Sequential read | | | | |
| Sequential write | | | | |
| Small files | | | | |
| Random read | | | | |
| Device-level | | | | |
| xSysInfo | | | | |
| Boot / real workload | | | | |

Do not force every benchmark into MiB/s.

For example:

- sequential operations → MiB/s;
- small-file test → files/s or elapsed time;
- random operations → operations/s or latency;
- boot → seconds.

---

# 16. Interpreting the 2×2 Matrix

## Case A — Bellatrix driver is consistently slower

Example:

~~~text
                   FAT        SFS

Bellatrix          3 MB/s     3 MB/s
Emu68             15 MB/s    14 MB/s
~~~

If this difference also exists in device-level testing, the Bellatrix driver becomes the primary suspect.

Investigate the driver/hardware path.

---

# 17. Case B — One Filesystem Is Slow Everywhere

Example:

~~~text
                   FAT        SFS

Bellatrix          4 MB/s    14 MB/s
Emu68              4 MB/s    15 MB/s
~~~

This points toward FAT or its configuration rather than a Bellatrix-specific SD problem.

The same reasoning applies if SFS is consistently slower with both drivers.

---

# 18. Case C — Filesystem/Driver Interaction

Example:

~~~text
                   FAT        SFS

Bellatrix         13 MB/s     3 MB/s
Emu68             14 MB/s    13 MB/s
~~~

This is particularly interesting.

The Bellatrix driver itself is capable of good throughput, and SFS itself is capable of good throughput.

The problematic combination is:

~~~text
Bellatrix driver + SFS
~~~

Investigate the request pattern generated by SFS and how the Bellatrix driver handles it.

---

# 19. Case D — Device-Level Fast, File-Level Slow

Suppose:

~~~text
Device-level:

Bellatrix       18 MB/s
Emu68           19 MB/s
~~~

but:

~~~text
Sequential file read:

Bellatrix        4 MB/s
Emu68           17 MB/s
~~~

This is extremely important evidence.

It means the Bellatrix implementation can transfer data quickly under at least one workload.

The next question becomes:

> What changes when requests originate through DOS/FAT/SFS?

Investigate:

- request sizes;
- request count;
- alignment;
- transfer splitting;
- `MaxTransfer`;
- `Mask`;
- buffering;
- synchronization;
- filesystem-specific request behavior.

---

# 20. Driver Instrumentation

If measurements point toward the Bellatrix driver, add aggregated instrumentation.

Avoid printing one debug line for every sector or request.

Logging itself can become the bottleneck.

Collect counters such as:

~~~text
read_requests
write_requests

bytes_read
bytes_written

minimum_request_size
maximum_request_size
average_request_size

read_errors
write_errors

retries
timeouts
~~~

Also collect a request-size histogram:

~~~text
512 B
1 KiB
2 KiB
4 KiB
8 KiB
16 KiB
32 KiB
64 KiB
>64 KiB
~~~

Where relevant:

~~~text
unaligned_reads
unaligned_writes

bounce_buffer_reads
bounce_buffer_writes
~~~

---

# 21. Request Granularity

This should be one of the first things examined if the drivers differ significantly.

Consider:

~~~text
Emu68 driver:

128 MiB transferred
4096 requests
average request = 32 KiB
~~~

versus:

~~~text
Bellatrix driver:

128 MiB transferred
262144 requests
average request = 512 B
~~~

Both eventually transfer exactly the same data.

Their performance characteristics will be completely different.

Therefore record not only:

~~~text
MiB/s
~~~

but also:

~~~text
requests
bytes/request
requests/MiB
~~~

---

# 22. MaxTransfer, Mask and Transfer Constraints

Compare the storage environment exposed by both driver configurations.

Inspect where applicable:

~~~text
MaxTransfer
Mask
block size
alignment requirements
DosEnvec
~~~

Incorrect or unnecessarily restrictive values may cause the filesystem to split requests.

For example:

~~~text
application requests 64 KiB
          │
          ▼
filesystem/device constraints
          │
          ▼
128 × 512-byte operations
~~~

could destroy performance even though the SD controller itself is capable of much larger transfers.

Do not assume that a performance difference originates inside the transfer loop itself.

---

# 23. Timing Instrumentation

If necessary, measure time inside the Bellatrix driver.

Useful categories include:

~~~text
total request time
controller wait time
data transfer time
~~~

Depending on the actual implementation, additional counters may include:

~~~text
poll iterations

DMA setup operations

cache maintenance operations

interrupts

buffer copies
~~~

Only instrument mechanisms that actually exist in the implementation.

---

# 24. Bellatrix-Specific Candidates

If evidence points toward the Bellatrix driver, investigate at least the following possibilities.

## 24.1 Excessive Polling

Determine whether significant time is spent waiting repeatedly for controller state changes.

## 24.2 Transfer Splitting

Determine whether large requests are unnecessarily divided into small transfers.

## 24.3 PIO/Data Copy Path

Determine whether the implementation performs expensive byte/word-level copying that the Emu68 driver avoids.

## 24.4 DMA and Bounce Buffers

If applicable, determine whether:

- alignment unnecessarily forces bounce buffers;
- data is copied multiple times;
- buffers are repeatedly prepared;
- cache maintenance is excessive.

## 24.5 Synchronization

Investigate unnecessary:

- interrupt disabling;
- `Forbid()/Permit()`;
- semaphores;
- busy waits;
- task switches.

Do not assume scheduler or interrupt problems merely because they have been investigated elsewhere in Bellatrix.

Require evidence from this workload.

## 24.6 Emu68/Bellatrix Boundary Cost

Determine whether the Bellatrix path performs substantially more transitions or expensive operations per request.

The useful metric is not merely:

~~~text
cost per transition
~~~

but:

~~~text
transitions per MiB
~~~

For example, an expensive operation performed once per 64 KiB may be insignificant.

The same operation performed once or several times per 512-byte sector may dominate the entire workload.

---

# 25. Instrumentation Policy

Use the existing Bellatrix harness and direct source inspection as the primary debugging workflow.

Prefer:

~~~text
reset counters
      │
      ▼
start benchmark
      │
      ▼
run workload without verbose logging
      │
      ▼
stop benchmark
      │
      ▼
dump aggregated counters
~~~

over:

~~~text
every request
      │
      ▼
serial printf
      │
      ▼
every sector
      │
      ▼
serial printf
~~~

Performance measurements made while heavily logging the hot path should not be considered representative.

---

# 26. Compare Against the Emu68 Driver Implementation

The Emu68 driver is not merely another benchmark result.

If it performs substantially better, use it as a reference implementation.

Compare concrete implementation choices such as:

- controller initialization;
- transfer mode;
- multi-block operations;
- request splitting;
- polling strategy;
- interrupt strategy;
- DMA/PIO behavior;
- cache handling;
- buffer alignment;
- retry behavior;
- synchronization;
- command sequencing.

The objective is not to copy the Emu68 driver blindly.

The objective is to identify **which implementation differences correspond to measured performance differences**.

---

# 27. Evidence Before Optimization

The investigation should follow:

~~~text
measure
   │
   ▼
reproduce
   │
   ▼
identify affected layer
   │
   ▼
instrument that layer
   │
   ▼
form hypothesis
   │
   ▼
test hypothesis
   │
   ▼
optimize
   │
   ▼
repeat identical benchmark
~~~

Avoid:

~~~text
SD feels slow
    │
    ▼
assume driver problem
    │
    ▼
rewrite driver
~~~

The 2×2 matrix exists specifically to prevent that mistake.

# 29. Immediate Deliverable

Do not begin by rewriting or optimizing the SD driver.

The first deliverable should be a reproducible baseline containing the four configurations:

~~~text
Bellatrix driver + FAT
Bellatrix driver + SFS

Emu68 driver + FAT
Emu68 driver + SFS
~~~

with at least:

~~~text
sequential read
sequential write
~~~

and, where practical:

~~~text
different I/O buffer sizes
small-file workload
random/seek workload
device-level measurement
xSysInfo result
real-world workload
~~~

If some tests cannot currently be executed, document why rather than modifying unrelated components merely to complete the matrix.

---

# 30. Success Criterion

The investigation succeeds when there is sufficient reproducible evidence to answer:

> **Is the observed SD performance loss caused primarily by the Bellatrix SD driver, the filesystem, an interaction between them, or a common higher/lower-level component?**

The next objective is then to answer:

> **What measurable implementation behavior explains the difference?**

Only after those questions have evidence-backed answers should performance optimization begin.
```
