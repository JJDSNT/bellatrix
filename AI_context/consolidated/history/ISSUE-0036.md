# Resolved (2026-08-17)

Fixed by `patches/aros/0023-fat-read-the-first-cluster-fields-little-endian.patch`,
commit `0c3a4ff`. `ENV:` populates — 22 files, 8 directories,
`ENV:SYS/theme.var` naming `THEMES:Ice` — and the desktop renders the Ice theme,
which had never happened on this port. Four headless runs reached it, and the
user confirmed it on their own boot.

Two things left this issue rather than died with it:

- **ISSUE-0037** — a TLSF free-list corruption in a CLI task, seen on one of the
  four runs. Code this fix makes reachable, not code it breaks. Parked until it
  recurs.
- **ISSUE-0038** — the handler is endian-correct now and still not endian-safe,
  because the on-disk fields are declared as native integers. Backlog.

The rest of this document is the diagnosis as it stood, kept because the
measurement is the part worth having.

# Summary

`ENV:` is empty on every boot. The Startup-Sequence populates it with

```
Copy >NIL: "ENVARC:" "ENV:" ALL NOPRO NOREQ PAT "~(def_#?.info)"
```

and that command copies **nothing, and says nothing**. Every `If EXISTS
"ENV:..."` after it therefore takes the `Else`, which means **no preference of
any kind loads** — the theme is only the visible half of it.

The symptom that started this was "no theme loads". The packaging was suspected
and is innocent: the card carries `theme.var`, `theme.default`, all ten themes,
`C:Decoration`, `decorator.library`, `decortheme.library`, `png.datatype` and
the `PNG` DataTypes descriptor. Nothing is missing. The copy is what fails.

# The defect

`external/aros/rom/filesys/fat/direntry.c`, `GetDirEntryByCluster()`:

```c
if (de->e.entry.first_cluster_hi == (cluster >> 16)
    && de->e.entry.first_cluster_lo == (cluster & 0xffff))
```

The two halves are little-endian on disk whatever the host is. `cluster` is
native. On a big-endian target the comparison **never matches**.

Its only caller is `GetParentDir()`, and only on the branch that looks the
parent up inside the grandparent — entered exactly when the parent directory is
not the root:

```c
if (dh->ioh.first_cluster != dh->ioh.sb->rootdir_cluster)   /* direntry.c:214 */
{
    ...
    err = GetDirEntryByCluster(dh, cluster, de, glob);      /* direntry.c:223 */
}
```

So **`ParentDir()` works at one level of depth and fails at two or more.** That
is a sharp, testable boundary, and it is the one that was measured.

The silence comes from `workbench/c/Copy.c:1826`:

```c
if (!(pdir = ParentDir(lock)))
{
    cd->RetVal = RETURN_ERROR;
    if (cd->Mode == COPYMODE_DELETE) { ...the only message... }
    UnLock(lock);
    return;
}
```

In copy mode that path prints nothing at all. Upstream even left a comment
four lines earlier — `// ParentDir() fuxored last round!` — so the fragility was
known to whoever wrote it.

# The measurement

On a card generated by `mcopy`, so the on-disk fields are correct by
construction. Instrumented Startup-Sequence writing to `SDCARD0P0:*.log`.

| source | parent's depth | result |
|---|---|---|
| `SDCARD0P0:S/Shell-Startup` | 1 | 94 bytes copied |
| `SYS:S/Shell-Startup` | 1 | 94 bytes copied |
| `S:Shell-Startup` | 1 | 94 bytes copied |
| `SYS:Prefs/Env-Archive` (`ALL`) | 2 | nothing, no message |
| `ENVARC:` (`ALL`, with and without `PAT`) | 2+ | nothing, no message |
| `ENVARC:SYS/theme.var` | 3 | nothing, no message |

`List "ENVARC:SYS/#?.var"` reads the same files fine, because listing walks
*down* and never asks for a parent.

An earlier hypothesis — "Copy cannot read through an assign" — is **false** and
was falsified by rows two and three above. It is recorded here because it looked
right for two probes and cost time.

# This was already found once, and deliberately left alone

`AI_context/consolidated/history/ISSUE-0007.md:819-882`, 2026-08-06. The
traversal was traced: with the comparison corrected, `GetParentDir()` succeeds
76 to 193 times per boot with the right names (`PREFS`, `ENV-AR~1`, `CLASSES`)
and zero errors, and `OpLockParent()` is called 860 to 1709 times per boot.

It was not fixed because fixing it **took the boot from 3 of 6 runs reaching the
desktop to 0 of 6**, dying in `C:Decoration` 13 times out of 13 once the theme
actually loaded. The verdict is recorded in `patches/aros/0006`'s own message:
the broken comparison is *accidentally load-bearing*, holding the boot up by
leaving half the system uninitialised.

**Why that verdict is worth re-testing now, and not simply trusted.** It was
measured on 2026-08-06, into a boot that was still intermittent from heap
corruption. Since then:

- `0007-kernel-refuse-to-free-a-pointer-outside-the-heap`,
- `0009-exec-name-the-caller-that-frees-outside-the-pool`,
- `0011-kernel-avoid-undersized-tlsf-free-blocks` — after which the boot
  intermittency ended on 2026-08-14.

A crash in `C:Decoration` — which allocates heavily, loads PNGs through
datatypes and builds decoration bitmaps — is exactly the shape of what those
fixed. The 0 of 6 may have been measuring the heap, not the theme. That is a
hypothesis, and the whole point of this issue is that it is now cheap to
falsify.

# The fix

`patches/aros/0023-fat-read-the-first-cluster-fields-little-endian.patch`,
three changes in `rom/filesys/fat`:

1. **`direntry.c`, `GetDirEntryByCluster()`** — compare `FIRST_FILE_CLUSTER(de)`
   against `cluster`. Decode the entry rather than encode the wanted value; the
   macro already exists at `fat_fs.h:304`. This is the defect.
2. **`ops.c`, `OpRenameFile()`** — was reassembling the raw halves and handing
   them to `CreateDirEntry()`, which since 0006 encodes what it is given. The
   missing decode and the added encode cancelled, so the bytes reached the disk
   correct *by accident*. Decode explicitly. No behaviour change on disk; the
   code stops being a coincidence.
3. **`volume.c`, `Format()`** — `bs_volid` was written natively while the mount
   path decodes it (`volume.c:246,256`), so the serial on the card was never the
   serial the volume reported.

`0023` also removes the comment `0006` left in `FillDirEntry()` saying the read
side is deliberately untouched, which stops being true with this applied.

# What is now clean, checked field by field

So this does not have to be re-derived: everything else in the handler already
converts, and the audit was exhaustive rather than sampled.

| field family | where | state |
|---|---|---|
| FAT12/16/32 table entries | `fat.c:125,147,158,198,236,256,278` | converted |
| FSInfo (`lead_sig`, `free_count`, `next_free`, …) | `fat.c:356-368`, `volume.c:386-391,652-656` | converted |
| long-name UTF-16 halves | `names.c:213-229,518-533` | converted |
| BPB | `compiler/fatbpb/bpb.c` — byte-wise `ReadLE16`/`ReadLE32` | endian-free |
| BPB written by `Format` | `volume.c:564-594` | converted |
| `file_size` | read `lock.c:227`, written `ops.c:889,1067` | converted (0006) |
| date and time words | `date.c` `ConvertFATDate`/`ConvertDOSDate` | converted (0008) |
| `first_cluster_{hi,lo}` | `fat_fs.h:304`, `direntry.c`, `ops.c` | **this patch** |

What is still raw is field-to-field copying (`ops.c:608-614`, Rename) and
locals holding the on-disk form between a read and a write-back
(`direntry.c:568-578`, `ops.c:1184-1190`). Neither interprets the value, so
neither needs to know the byte order.

# Upstream

Still present in `origin/master` as of 2026-08-17 — checked, `direntry.c:242` is
unchanged. 50 commits landed since our pin (`8570536`, 2026-08-13) and none
touches it. `workbench/c/Copy.c` has not been touched since 2025;
`rom/dos/match*.c` since 2021. The one nearby commit is `a79ba11263`
(2026-06-15, *fat: strip leading volume/assign specifier in LockFileByName*),
already in our pin and a different problem.

This is an upstream defect on **every big-endian AROS target** — `m68k-amiga`,
`ppc-native` and `ppc-morphos` share this code — and it means parent-directory
resolution has never worked on any of them on FAT. Candidate for
`ISSUE-0015`'s upstream ledger.

# What to do

1. Build lean and boot. The first question is not the theme: it is whether
   `ENV:` gets populated at all.
2. If it does, the second question is whether `C:Decoration` still kills the
   boot. Measure it as a series, alternating with the pre-fix ELF, per the
   boot-measurement discipline.
3. If it does kill the boot, that crash is a **new issue**, not a reason to
   revert this one. The FAT read path is either correct or it is not; a
   downstream defect it exposes is a second bug, and 0006's own message says as
   much.

# Notes

**This is inside the standing freeze.** Nothing is being added: a filesystem
that cannot resolve a parent directory below two levels is not a stable system,
and a boot where no preference loads is not a working desktop.

**Do not read a working `Copy` as "the theme now works".** Those are two claims
and the second one has been wrong before.
